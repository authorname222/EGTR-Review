# FAQ

### Q1. The student weights are 14 GB — where do I get them?

See `checkpoints/README.md`. During the review period we host the LoRA adapter
on an anonymous mirror. Upon acceptance the weights will be released through a
regular channel.

### Q2. Can the distilled supervision data be redistributed?

The `T_i` and `Y_i` triples are generated by GPT-5.1. Redistribution must follow
OpenAI's current usage policy. We provide only small samples in this repository
for research evaluation under the EMNLP review.

### Q3. SerpApi is paid; can reviewers still run the demo?

Yes. The evidence retriever caches results under
`data/samples/distilled/cached_evidence/`. Pass `--use_cached_retrieval` (read
by the retriever from `configs/retrieval.yaml :: cache.enabled`) to bypass the
API call entirely.

### Q4. Why aren't PDFs of the source papers included?

Two reasons: (1) PDF metadata is a common identity-leak vector and (2)
redistribution of OpenReview-hosted PDFs is forbidden by their Terms of
Service. We ship JSON content extracts only.

### Q5. Where are the prompts?

`docs/prompts/`. All five agent prompts are reproduced verbatim there; the
verifier's flag-conditioned strategies live in `src/agents/verification_reasoner.py`.

### Q6. How are ablations switched on / off?

Through `configs/student_train.yaml :: ablation`. The four switches are:

- `use_reasoning_supervision`
- `use_task_prefix`
- `use_evidence_labels`
- `use_evidence_weighting`

`scripts/reproduce_ablation.sh` walks through all four single-switch variants.

### Q7. The LLM-as-Judge needs three different APIs (Gemini, DeepSeek, Claude). How do I configure them?

Set `{GEMINI,DEEPSEEK,CLAUDE}_API_KEY` and `{GEMINI,DEEPSEEK,CLAUDE}_BASE_URL`
environment variables. The judge defaults to OpenAI-compatible chat completion
clients, so any OpenAI-compatible proxy works. Cached judgments in
`data/samples/cached_llm_judgments.json` allow verification without API access.

### Q8. The teacher pipeline crashes mid-way through 1000 papers; can I resume?

Yes. The teacher writes per-paper JSON files under `--output`, so re-running
the pipeline skips already-completed papers. Each run also appends one line
per paper to `<output>/resume_log.jsonl` so you can audit a partial run:

```bash
# Quick summary of the current state (no API calls).
python -m src.teacher_pipeline --output <output_dir> --status

# Just the IDs that failed.
jq -r 'select(.event == "paper_failed") | .paper_id' <output>/resume_log.jsonl

# Average per-paper LLM cost so far.
jq 'select(.event == "paper_completed") | .llm_prompt_tokens + .llm_completion_tokens' \
   <output>/resume_log.jsonl | awk '{s+=$1; n++} END {print s/n}'
```

Failed papers leave a `paper_failed` event with `error` + `stage` so you can
investigate without re-running the whole batch. To retry only the failures:
delete their (non-existent) outputs is a no-op, so just re-run the same
`scripts/run_teacher_pipeline.sh` — the resume logic re-attempts every paper
that has no `<paper_id>.json` yet, including previously failed ones.

### Q9. Why does the leak-filter target `openreview.net`?

To prevent the teacher's external retrieval from indirectly observing
ground-truth reviews / rebuttals / decisions during data construction. See
`src/utils/leak_filter.py`.
